## 3. “完整量化实验”与“最小演示”到底做到什么程度
## 3.1 ARM 完整量化实验（首稿必做）
1. 数据规模  
默认 `10,000` 测试样本（MNIST 全测试集）。

2. 配置固定  
固定权重版本、位宽、阈值、timesteps、预处理方式，写入实验表。

3. 必交付指标  
Accuracy、Latency、Throughput、资源、功耗、时序（WNS）。

4. 必交付证据  
日志、预测结果文件、统计脚本、图表、commit id、配置文件哈希。

5. 验收门槛  
`FPGA vs Python` 误差在可解释范围内；流程可重复跑通。

## 3.2 E203 最小演示（首稿必做）
1. 功能打通  
E203 能完成寄存器配置、DMA 触发、CIM 触发、结果读取。

2. 样本要求  
至少 `1` 个样本正确跑通；建议 `10~100` 样本 smoke 稳定性测试。

3. 必交付证据  
UART 日志、关键寄存器读写记录、DONE 位轮询结果、关键波形截图。

4. 验收门槛  
连续运行无死锁、无超时、输出非空且流程稳定。

## 3.3 E203 完整量化实验（扩展包，供导师决策）
1. 与 ARM 同口径  
同样做大样本（优先 10k），输出同类指标。

2. 为何耗时大  
接入与调试链路复杂，控制面速度慢于 ARM，批量采样脚本成熟度低。

3. 启动条件  
ARM 全量结果先齐，再评估是否升级首稿。

## 4. ARM 与 E203 分工（详细版）
1. ARM 负责什么  
快速、稳定、大批量地采集论文主数据。  
这是“软件控制硬件加速”的路径，不是纯软件推理。

2. E203 负责什么  
证明“自研 CPU + 自研加速器”的系统完整性和可编程控制面。

3. 为什么 ARM 被叫软件路径  
ARM 用软件代码发控制命令；计算仍由硬件链路执行。  
所以是“软件控制路径”，不是“软件计算路径”。

4. 首稿最优组合  
ARM 做主结果，E203 做完整性证据。  
这是时间和说服力的最优平衡点。

## 5.1 首稿建议纳入（低风险、高可解释）
| 创新点 | 是否纳入首稿 | 原因 | 需要的数据证据 |
|---|---|---|---|
| 活动检测 + 计算跳过 | 建议纳入 | 逻辑简单，直接对应能效叙事 | 跳过前后时延/功耗对比 |

| 点 | 建议 | 原因 |
|---|---|---|

| 创新点 | 延后原因 |

# FPGA论文与工程执行总计划（更新版：含5.1创新点、性能计数器与中断、E203边界）

> 版本：v2026-03-03

## 一、摘要
1. 本计划目标是在不改变当前主线`main`“MVP状态”事实的前提下，完成一条可投稿SCI的FPGA论文路径，并保证工程可复现、可解释、可答辩。

4. 性能计数器寄存器作为“论文证据链核心”，中断模式作为“工程可用性增强”并纳入实现。
5. 对“为什么暂不做E203全量”给出工程、时间、评审三层可辩护理由。

## 二、执行四原则（统一口径）
1. 先建立基线：先跑稳`ARM主路径完整量化 + E203最小闭环`，拿到“无创新点”基线数据。

## 三、当前基线状态（写入计划前提）
1. `main`当前仍是MVP主线状态，AXI/UART/SPI主集成未全部落地到`main`顶层。
2. 相关能力主要仍在各feature分支推进，文档已同步分支进度口径。
3. 本计划不要求先把所有feature一次性并回`main`后再做论文，而是先打通“可验证、可投稿”的FPGA路线。

## 四、论文定位与叙事主线（面向非数字背景老师可读）
1. 论文定位：这是“面向CIM-SNN系统的软件可控硬件仿真器/原型平台”，不是纯粹追求峰值TOPS的通用GEMM加速器。
2. 核心价值：把“算法-硬件接口-系统行为”连成闭环，证明可部署、可测量、可扩展。
3. 为什么不用纯软件仿真：软件能算对，但不能真实反映总线、寄存器、时序、并行数据流、外设交互和硬件瓶颈。

## 五、ARM与E203分工（详细解释）
1. ARM路径（软件路径）的定义：“软件路径”指由ARM端程序负责加载权重、配置寄存器、启动计算、读取结果、统计性能。它像“总调度员”，不直接做大规模乘加。
2. E203路径的定义：E203是片上轻量控制核，更适合演示“嵌入式自主控制”能力，不适合当前阶段做大规模全量评测主力。
3. 为什么ARM叫软件路径：因为它运行可编译的软件（C/C++/Python驱动层），通过寄存器API控制硬件。硬件仍在PL/CIM侧执行核心计算。
4. 为什么E203暂不适合全量（必须写入论文方法章节）：
   - 工程层：工具链、驱动、数据搬运链路尚不如ARM成熟。
   - 资源层：E203侧可用内存与I/O生态不利于大样本量实验。
   - 时间层：到2026-06-30，做E203全量会吞噬大量联调时间。
   - 评审层：首稿更看重“结果完整+可复现”，不是“所有CPU都跑全量”。
5. 结论：首稿采用`ARM全量 + E203最小演示`，E203全量列为二期扩展。

## 七、5.1创新点（详细落地版）
### 5.1.1 稀疏感知计算跳过（必做）
1. 内容：输入全零或低活动时跳过部分无效计算周期。
2. 实现：增加活动检测门控与跳过计数，不改变功能正确性。
3. 指标：跳过率、周期下降比例、精度变化（应接近0）。
4. 风险控制：只在“严格可判定无贡献”条件触发跳过。

### 5.1.2 稀疏性统计与可解释调优（必做）
1. 内容：把spike活动、阻塞、有效帧数变成可读统计数据。
2. 实现：依赖性能计数器寄存器输出，并形成实验脚本。
3. 指标：不同输入下的稀疏分布与延迟对应关系。
4. 论文价值：把“为什么快/慢”从主观描述变成数据证据。

### 5.1.3 Shadow Buffer轻量双缓冲（建议做）
1. 内容：计算与数据准备重叠，减少空转等待。
2. 实现：双缓冲切换FSM，避免复杂总线重构。
3. 指标：帧间空泡减少、帧吞吐提升。
4. 降级策略：若时序风险高，可降级为单缓冲并保留接口。

### 5.1.4 可观测性即创新（计数器+中断）（必做）
1. 内容：不仅“跑通”，还要“可测、可证、可复现”。
2. 实现：标准寄存器计数器 + 可屏蔽中断模式 + 统一采样协议。
3. 指标：重复实验方差、日志可复现性、调试时间缩短。

## 八、性能计数器寄存器与中断模式（详细规格）
### 7.1 现有计数器寄存器（保持兼容）
| 地址偏移 | 名称 | 位域定义 | 用途 |
|---|---|---|---|
| 0x30 | REG_DBG_CNT_0 | [31:16] `cim_cycle_cnt`, [15:0] `dma_frame_cnt` | 计算周期与帧计数 |
| 0x34 | REG_DBG_CNT_1 | [31:16] `wl_stall_cnt`, [15:0] `spike_cnt` | 阻塞与活动统计 |
| 0x2C | REG_CIM_TEST | 按现有定义 | 调试辅助 |

说明：现有计数器为16位子字段拼接，读数必须做差分与回绕处理。

### 7.2 统一采样协议（必须执行）
1. 运行前读一次`0x30/0x34`作为`before`。
2. 跑N帧后再读一次作为`after`。
3. 每个16位字段做`delta = (after - before) mod 65536`。
4. 计算核心指标：
   - `cycles_per_frame = delta_cim_cycle / max(delta_dma_frame,1)`
   - `stall_ratio = delta_wl_stall / max(delta_cim_cycle,1)`
   - `spike_per_frame = delta_spike / max(delta_dma_frame,1)`
5. 所有论文图表基于差分值，不直接用瞬时寄存器原值。

### 7.3 中断模式（本次纳入）
新增寄存器（不破坏旧接口，地址按当前空洞顺延）：
| 地址偏移 | 名称 | 位定义 |
|---|---|---|
| 0x38 | REG_IRQ_STATUS | bit0 frame_done, bit1 dma_done, bit2 timeout, bit3 error |
| 0x3C | REG_IRQ_MASK | 对应位1=使能中断上报 |
| 0x40 | REG_IRQ_CLEAR | 写1清对应状态位（W1C） |
| 0x44 | REG_TIMEOUT_CYC | 超时阈值 |

中断行为规范：
1. 事件置位`STATUS`，若`MASK`使能则拉高`irq_out`。
2. 软件读`STATUS`确认来源，写`CLEAR`清除，再进入下一帧。
3. 中断不可用时自动回退到轮询模式，不影响功能正确性。

### 7.4 采样框架与日志脚本定义（统一口径）
1. 定义：
   - 计数器采样框架：固定测量协议（何时读、怎么算、怎么算指标）。
   - 日志脚本：自动执行采样协议并输出可复现实验证据。
2. 采样流程（必须）：
   - 运行前读`0x30/0x34`作为`before`。
   - 跑N帧后再读`0x30/0x34`作为`after`。
   - 每个16位字段计算`delta = (after - before) mod 65536`。
   - 禁止使用瞬时寄存器值直接作图。
3. 指标计算口径：
   - `cycles_per_frame = delta_cim_cycle / max(delta_dma_frame,1)`
   - `stall_ratio = delta_wl_stall / max(delta_cim_cycle,1)`
   - `spike_per_frame = delta_spike / max(delta_dma_frame,1)`
4. 日志脚本最低输出字段：
   - `run_id`、`git_commit`、`mode(ARM/E203)`、`dataset`、`clock_mhz`
   - `quant_cfg`、`frames`、`before_raw`、`after_raw`、`delta_*`
   - `accuracy`、`latency`、`throughput`
5. 常见错误（必须规避）：
   - 不做差分；忽略16位回绕；混入warm-up数据；
   - 跨配置横向比较；不记录commit导致结果不可追溯。

## 九、公开接口/API/类型变更
1. 对外寄存器接口新增`IRQ_STATUS/IRQ_MASK/IRQ_CLEAR/TIMEOUT`四个寄存器。
2. 现有寄存器地址与位义保持不变，属于向后兼容扩展。
3. 软件API新增：`snn_run_frame_blocking()`、`snn_wait_irq(timeout_ms)`、`snn_read_perf_delta()`、`snn_clear_irq(flags)`。
4. 文档接口新增：统一的“寄存器手册页 + 计数器采样模板 + 中断时序图”。
5. 预留日志CLI接口（文档先定义）：
   - `perf_collect --mode {arm|e203} --frames N --quant CFG --out result.csv`
   - `perf_analyze --in result.csv --out summary.json`
